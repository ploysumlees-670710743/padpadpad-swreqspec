# แผนร่าง: จัดกลุ่มและฝ่ายงาน

อ้างอิง: `specs/004-groupmanagement/spec.md` (Draft v2, SPEC-GRP-004)

## 1. สรุปแนวทาง

1. ระบบให้ผู้ใช้ที่มีบัญชีและบทบาท `committee` จัดบ้านให้สมาชิกหลักและสุ่มจัดผู้เข้าร่วมค่ายชั้นปีที่ 1–2 (FR-GRP-01 ถึง FR-GRP-04, CON-GRP-02, CON-GRP-06).
2. แสดงผลร่างให้ตรวจและแก้บ้านหรือฝ่ายงานก่อนยืนยัน โดยรองรับการสุ่มใหม่และแทนที่ผลสุ่มเดิม (FR-GRP-03, FR-GRP-05, FR-GRP-08, FR-GRP-10).
3. ตรวจเงื่อนไขสังกัดหนึ่งบ้านต่อคนและบ้านพร้อมฝ่ายงานหนึ่งชุดต่อกรรมการ ก่อนบันทึกผล (CON-GRP-03, CON-GRP-04, CON-GRP-08, NFR-DATA-01).
4. การบันทึกครั้งแรกประกาศผลและล็อกการแก้ไข จากนั้นแจ้งสมาชิกทั้งหมด พร้อมเก็บสถานะการแจ้งที่ล้มเหลวโดยไม่ย้อนข้อมูลสังกัด (FR-GRP-06, FR-GRP-07, FR-GRP-09, CON-GRP-07).
5. ออกแบบข้อมูล/API/UI และทดสอบตาม AC ทุกข้อ โดยไม่เลือกช่องทางแจ้งเตือนหรือสูตรวัดความสมดุลนอกเหนือจากที่ทีมกำหนด (AC-GRP-01 ถึง AC-GRP-04, Q-01).

## 4. API / หน้าจอ

### API

| Method / path | Input / output หลัก | รองรับ |
|---|---|---|
| `GET /api/group-management/assignments` | output: รายชื่อสมาชิกที่เข้าเงื่อนไข, บ้าน, ฝ่ายงาน, สังกัดและสถานะ | FR-GRP-01, FR-GRP-02, FR-GRP-07, IF-GRP-01, IF-GRP-02 |
| `POST /api/group-management/drafts/randomize` | input: ไม่มีข้อมูลสมาชิกจากผู้เรียก; output: ผลสุ่มร่างแทนผลสุ่มเดิม | FR-GRP-03, CON-GRP-05, CON-GRP-06, IF-GRP-03 |
| `PUT /api/group-management/drafts/assignments/{member_id}` | input: `house_id`, `department_id` ตามประเภทสมาชิก; output: สังกัดร่างหลังตรวจเงื่อนไข | FR-GRP-02, FR-GRP-04, FR-GRP-08, FR-GRP-10, CON-GRP-02 ถึง CON-GRP-04, CON-GRP-08 |
| `POST /api/group-management/drafts/confirm` | input: การยืนยันผลร่าง; output: สถานะบันทึก/ประกาศและสถานะส่งแจ้งรายสมาชิก | FR-GRP-05, FR-GRP-06, CON-GRP-07 |
| `GET /api/group-management/notifications` | output: สถานะการแจ้งรายสมาชิกที่สำเร็จ/ล้มเหลว | FR-GRP-06, ASM-12; ช่องทางและผู้มีสิทธิ์ตรวจสอบยังรอคำตอบ Q-01 |
| `POST /api/group-management/notifications/{delivery_id}/retry` | input: `delivery_id`; output: สถานะการส่งซ้ำ | FR-GRP-06, ASM-12; ช่องทางและผู้มีสิทธิ์ส่งซ้ำยังรอคำตอบ Q-01 |

ทุก endpoint ที่เปลี่ยนสังกัดตรวจบทบาท `committee` และปฏิเสธการแก้สังกัดหลังสถานะ published (CON-GRP-02, CON-GRP-07, NFR-SEC-01). ผู้มีสิทธิ์ตรวจสถานะหรือส่งแจ้งเตือนซ้ำยังไม่กำหนด; ไม่ถือว่าเป็น role `committee` โดยอัตโนมัติ และคงเป็นส่วนที่รอคำตอบ Q-01.

## 7. ลำดับงาน

1. เชื่อมข้อมูล roster, บ้าน, ฝ่ายงาน และตรวจบทบาทผู้ใช้ โดยไม่แก้ข้อมูลต้นทาง (FR-GRP-01, FR-GRP-02, CON-GRP-01, CON-GRP-02, IF-GRP-01, IF-GRP-02, IF-GRP-03).
2. สร้างโมเดลสังกัดร่าง/ประกาศและกฎความสัมพันธ์ unique ต่อสมาชิก (CON-GRP-03, CON-GRP-04, NFR-DATA-01).
3. สร้าง service กำหนดสมาชิกหลักชั้นปี 3–4 และสุ่มผู้เข้าร่วมชั้นปี 1–2; ปิดจุดตัดสินสูตรสมดุลกับทีมก่อนเลือกอัลกอริทึม (FR-GRP-02, FR-GRP-03, CON-GRP-05, CON-GRP-06).
4. สร้าง API/UI รายชื่อ บ้าน ฝ่ายงาน และการแก้ร่างพร้อม confirmation (FR-GRP-01, FR-GRP-02, FR-GRP-04, FR-GRP-08, FR-GRP-10).
5. สร้างหน้าผลตรวจสอบและยืนยันครั้งแรก; persist ผลและล็อกก่อนเริ่มส่งแจ้งเตือน (FR-GRP-05, FR-GRP-06, CON-GRP-07, CON-GRP-08).
6. เพิ่มการแจ้งสมาชิกและสถานะรายผู้รับ การตรวจสอบ/ส่งซ้ำ โดยรอคำตอบช่องทางจาก Q-01 ก่อนเลือก provider (FR-GRP-06, ASM-12, Q-01).
7. สร้างการอ่านสังกัดปัจจุบันและสถานะ “จัดสังกัดแล้ว” ให้ผู้ใช้เห็น (FR-GRP-07).
8. เขียนและรัน unit/API/UI tests ตาม AC ทั้งสี่ข้อ รวมสิทธิ์ ความครบถ้วน การบันทึก การล็อก และกรณีส่งแจ้งเตือนล้มเหลว (AC-GRP-01 ถึง AC-GRP-04).

## 8. สิ่งที่ยังไม่ทำ

- **Q-01** ระบบต้องแจ้งสมาชิกที่ได้รับการจัดสังกัดผ่านช่องทางใด? ผู้ที่ต้องตอบ: ทีมเอง. ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (ห้ามเลือก provider/ช่องทางแทนทีม; วางได้เพียง interface และสถานะการส่งที่ไม่ผูก provider).

- เกณฑ์ “จำนวนและสัดส่วนชายหญิงให้ใกล้เคียงกันมากที่สุด” ยังไม่มีสูตรหรือวิธีตัดสินกรณีผลเสมอใน spec (CON-GRP-05, AC-GRP-02). ยังไม่เลือกสูตรหรือ tie-break เอง; ส่วนอัลกอริทึมและเกณฑ์ผ่าน AC นี้จะยังไม่สรุปจนกว่าทีมกำหนด.

- ฐานข้อมูลไม่ได้ระบุใน Constraints; ยังไม่เลือกฐานข้อมูลหรือ migration tool (ทีมเลือกเอง ไม่ได้มาจาก spec).

## ข้อสังเกตสำหรับทีม

- Constraint ที่ยังใช้ไม่ครบ: CON-GRP-05 เพราะคำว่า “ใกล้เคียงกันมากที่สุด” ยังไม่มีเกณฑ์เชิงคำนวณ; ส่วน CON/IF อื่นมีจุดนำไปใช้ในแผน.
- AC ที่ทดสอบยาก: AC-GRP-02 จนกว่าจะกำหนดนิยามเชิงตัวเลข/สูตรสมดุล; AC-GRP-03 ทดสอบการจัดการความล้มเหลวด้วย mock ได้ แต่ทดสอบช่องทางจริงไม่ได้จนกว่าจะตอบ Q-01.
- สิ่งที่ไม่เดา: สูตรสมดุลและวิธีจัดการผลเสมอ, ช่องทาง/provider แจ้งเตือน, สิทธิ์ตรวจหรือส่งซ้ำแจ้งเตือน และฐานข้อมูล.

# แผนงาน: จัดการตารางกิจกรรมและ checklist

## 1. สรุปแนวทาง
1. ระบบจะแสดงตารางกิจกรรมค่ายให้ผู้ใช้ที่ได้รับสิทธิ์จัดการเพิ่ม แก้ไข หรือลบกิจกรรมย่อย และให้ผู้ใช้ที่มีสิทธิ์ดูสามารถดูตารางได้ตาม CON-SCH-03 และ NFR-SEC-01
2. ฟอร์มกิจกรรมย่อยจะรับวัน ช่วงเวลาเริ่ม-สิ้นสุด สถานที่ รายละเอียด และวิทยากร/ผู้รับผิดชอบ โดยบังคับกรอกข้อมูลรายละเอียดและผู้รับผิดชอบให้ครบตาม FR-SCH-02 และ ASM-03
3. ระบบจะตรวจสอบกิจกรรมที่ใช้สถานที่เดียวกันและมีช่วงเวลาซ้อนทับก่อนบันทึก ส่วนกิจกรรมที่ใช้สถานที่เดียวกันแต่เวลาไม่ซ้อนทับกันจะบันทึกได้ตาม CON-SCH-01 และ ASM-02
4. ระบบจะปฏิเสธรายการที่ซ้ำซ้อนและแสดงข้อผิดพลาดบริเวณข้อมูลช่วงเวลา/สถานที่ เพื่อให้ผู้มีสิทธิ์แก้ไขก่อนบันทึกตาม FR-SCH-04
5. กิจกรรมใหม่จะมีสถานะ checklist เป็น Pending และรองรับการติดตามสถานะ Done/Pending โดยการบันทึกกิจกรรมใช้ Database Transaction และตรวจ p95 <= 1 วินาทีตาม NFR ที่เกี่ยวข้อง

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างหน้าตารางกิจกรรม ฟอร์มกิจกรรม และการแสดงข้อผิดพลาดบริเวณฟิลด์ |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้าง API สำหรับตารางกิจกรรม การตรวจซ้ำ และสถานะ checklist |
| PostgreSQL | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้เก็บโครงการค่าย สถานที่ กิจกรรมย่อย และสถานะ checklist |
| ระบบยืนยันสิทธิ์ผู้ใช้ | CON-SCH-03, NFR-SEC-01 | API ทุกคำสั่งเพิ่ม แก้ไข ลบ และบันทึกต้องตรวจสิทธิ์จัดการ |
| Database Transaction | NFR-REL-01 | ใช้ครอบคลุมการตรวจซ้ำและการบันทึกกิจกรรม เพื่อป้องกันการบันทึกไม่ครบถ้วน |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ FR/CON |
|---|---|---|
| CampProject | project_id, project_name, status | รองรับ CON-SCH-02 และ ASM-01 โดยเป็นข้อมูล Precondition ที่ต้องมีอยู่ก่อน |
| CampLocation | location_id, project_id, location_name | รองรับ CON-SCH-02, CON-SCH-01 และ ASM-01 |
| SubActivity | activity_id, project_id, location_id, activity_name, activity_date, start_time, end_time, description, facilitator_or_responsible, checklist_status, created_by, updated_by | รองรับ FR-SCH-01 ถึง FR-SCH-05, CON-SCH-01 ถึง CON-SCH-03 และ ASM-02 ถึง ASM-05 |
| UserPermission | user_id, role, can_view_schedule, can_manage_schedule | รองรับ CON-SCH-03 และ NFR-SEC-01 |

หมายเหตุ:
- `checklist_status` รับค่า `Done` หรือ `Pending` ตาม FR-SCH-01 และ ASM-04 โดยกิจกรรมใหม่เริ่มต้นเป็น `Pending`
- ไม่สร้างโมเดลสำหรับการประกาศผลหรือการแจ้งเตือนแบบเรียลไทม์ เพราะอยู่ใน Out of scope
- `CampProject` และ `CampLocation` เป็นข้อมูล Precondition จึงไม่รวมฟังก์ชันสร้างข้อมูลโครงการค่ายหรือสถานที่ใน feature นี้

## 4. API / หน้าจอ

| ชื่อ | Input/Output หลัก | รองรับ |
|---|---|---|
| GET /schedule | Input: project_id และสิทธิ์ดู; Output: ตารางกิจกรรมย่อยพร้อมรายละเอียด ผู้รับผิดชอบ และสถานะ Done/Pending | FR-SCH-01, CON-SCH-02, CON-SCH-03, NFR-SEC-01 |
| POST /schedule/activities | Input: วัน เวลา สถานที่ ชื่อกิจกรรม รายละเอียด และวิทยากร/ผู้รับผิดชอบ; Output: กิจกรรมที่บันทึกหรือข้อผิดพลาดที่ฟิลด์ซ้ำ | FR-SCH-02, FR-SCH-03, FR-SCH-04, FR-SCH-05, CON-SCH-01, NFR-REL-01 |
| PUT /schedule/activities/{activity_id} | Input: ข้อมูลกิจกรรมที่แก้ไขและสิทธิ์จัดการ; Output: กิจกรรมที่แก้ไขหรือข้อผิดพลาดความซ้ำซ้อน | FR-SCH-01, FR-SCH-02, FR-SCH-03, FR-SCH-04, FR-SCH-05, CON-SCH-01, CON-SCH-03 |
| DELETE /schedule/activities/{activity_id} | Input: activity_id และสิทธิ์จัดการ; Output: ผลการลบกิจกรรม | FR-SCH-01, CON-SCH-03, NFR-SEC-01 |
| PATCH /schedule/activities/{activity_id}/checklist | Input: สถานะ `Done` หรือ `Pending` และสิทธิ์จัดการ; Output: สถานะ checklist ล่าสุด | FR-SCH-01, CON-SCH-03, NFR-SEC-01 |
| หน้า Schedule Management | แสดงตาราง ฟอร์มเพิ่ม/แก้ไข/ลบ ฟิลด์บังคับ สถานะ checklist และข้อผิดพลาดบริเวณช่วงเวลา/สถานที่ | FR-SCH-01, FR-SCH-02, FR-SCH-04, CON-SCH-03, NFR-SEC-01 |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| CON-SCH-01 | ฟังก์ชันตรวจช่วงเวลาและสถานที่ใน POST/PUT และ transaction ก่อนบันทึก โดยเวลาไม่ซ้อนทับกันสามารถใช้สถานที่เดียวกันได้ | ใช้แล้ว |
| CON-SCH-02 | ใช้ `CampProject` และ `CampLocation` เป็นข้อมูล Precondition และตรวจ `project_id`/`location_id` ก่อนสร้างหรือแก้ไขกิจกรรม | ใช้แล้ว |
| CON-SCH-03 | `UserPermission`, middleware สิทธิ์ และการตรวจสิทธิ์ใน POST/PUT/DELETE/PATCH; ผู้ไม่มีสิทธิ์ดูได้อย่างเดียว | ใช้แล้ว |
| NFR-PERF-01 | ทดสอบ endpoint POST/PUT ที่ตรวจความซ้ำซ้อนและบันทึกกิจกรรมด้วย p95 <= 1 วินาที | ใช้แล้ว |
| NFR-SEC-01 | บังคับตรวจสิทธิ์จัดการก่อนเพิ่ม แก้ไข ลบ หรือบันทึก และอนุญาตการดูแก่ผู้ไม่มีสิทธิ์จัดการ | ใช้แล้ว |
| NFR-REL-01 | ใช้ Database Transaction ครอบคลุมการตรวจซ้ำและบันทึกกิจกรรม รวมถึง rollback เมื่อบันทึกไม่ครบ | ใช้แล้ว |

## 7. ลำดับงาน

1. เตรียมการอ่านข้อมูล `CampProject` และ `CampLocation` ที่เป็น Precondition พร้อมตรวจสิทธิ์ผู้ใช้ (CON-SCH-02, CON-SCH-03, ASM-01)
2. สร้างโมเดล `SubActivity`, `UserPermission` และฟิลด์ checklist `Done/Pending` โดยตั้งกิจกรรมใหม่เป็น `Pending` (FR-SCH-01, ASM-04)
3. สร้างหน้าตารางและฟอร์มกิจกรรมที่มีฟิลด์บังคับครบ รวมการเพิ่ม แก้ไข ลบ และแสดงสถานะ checklist (FR-SCH-01, FR-SCH-02, CON-SCH-03)
4. สร้างตัวตรวจความซ้ำซ้อนโดยเปรียบเทียบสถานที่เดียวกันกับช่วงเวลาที่ทับกัน และอนุญาตกรณีเวลาไม่ซ้อนทับ (FR-SCH-03, CON-SCH-01, ASM-02)
5. สร้าง API บันทึก/แก้ไขด้วยการปฏิเสธรายการซ้ำและแสดงข้อผิดพลาดที่ฟิลด์ช่วงเวลา/สถานที่ (FR-SCH-04, FR-SCH-05, AC-SCH-02)
6. ครอบการตรวจซ้ำและการบันทึกด้วย Database Transaction พร้อม rollback เมื่อบันทึกไม่ครบ (NFR-REL-01)
7. เพิ่มการตรวจสิทธิ์สำหรับผู้จัดการและสิทธิ์ดูสำหรับอาจารย์/เจ้าหน้าที่ฝ่ายงาน รวมทดสอบการลบและแก้ไข (CON-SCH-03, NFR-SEC-01)
8. ทดสอบ AC-SCH-01 และ AC-SCH-02 พร้อมวัด p95 ของการตรวจซ้ำและบันทึกให้ไม่เกิน 1 วินาที (NFR-PERF-01)

## 8. สิ่งที่ยังไม่ทำ

ไม่มี Open Questions ใน spec v2 ของ feature นี้ ส่วนที่อยู่นอกขอบเขตและจะยังไม่สร้างคือ:
- การสร้างข้อมูลโครงการค่ายและสถานที่จัดค่าย เพราะเป็น Precondition ตาม CON-SCH-02 และ ASM-01
- การประกาศผลหรือส่งแจ้งเตือนการเปลี่ยนแปลงตารางกิจกรรมไปยังนักศึกษา/อาจารย์แบบเรียลไทม์ เพราะอยู่ใน Out of scope

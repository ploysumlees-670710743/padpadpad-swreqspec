# Feature: สมัครเข้าร่วมค่าย (Camp Enroll)
Spec ID: SPEC-ENR-011 | Source: SRS v1.0 (UC-11) | Use case: UC-11
Owner: ทีมพัฒนาระบบค่าย | Status: Draft v4 | Change Request: CR-011-01 | Updated: 2569-11-08

## Goal
แอปพลิเคชันนี้รองรับค่ายเดียว โดยนักศึกษาเข้าสู่ฟอร์มสมัครของค่ายนั้นได้โดยตรงโดยไม่ต้องเลือกค่าย
Backend กำหนด `camp_id` จาก Environment Variable `CAMP_ID` ภายในระบบและไม่รับ `camp_id` จากผู้สมัคร
นักศึกษากรอกข้อมูลผู้สมัครและข้อมูลการแพ้อาหารโดยไม่ต้องแนบเอกสาร บันทึกและกลับมากรอก Draft ของตนเองต่อได้ โดย Draft ยังไม่ถือเป็นใบสมัครที่ส่งแล้ว
เมื่อส่งข้อมูลที่ผ่านการตรวจสอบ ระบบจะเปลี่ยนเป็นใบสมัครสถานะ `submitted` ซึ่งแสดงแก่ผู้สมัครว่า "รอตรวจสอบ"

## Scope
### In scope
- เปิดฟอร์มสมัครของค่ายเดียวที่ระบบกำหนดให้นักศึกษาโดยตรง โดยไม่แสดงรายการหรือขั้นตอนเลือกค่าย
- กรอกข้อมูลสมัครเข้าร่วมค่าย
- กรอกข้อมูลผู้สมัครตามฟิลด์ที่กำหนด และเลือกชั้นปี 1–6 หรืออื่นๆ พร้อมระบุรายละเอียด
- ระบุข้อมูลการแพ้อาหาร โดยเมื่อเลือก “มี” ต้องกรอกรายละเอียด
- บันทึกและโหลด Draft ของผู้สมัครแต่ละคนหนึ่งรายการสำหรับค่ายนี้
- ตรวจสอบความครบถ้วนและรูปแบบของข้อมูลสมัคร
- บันทึกข้อมูลการสมัคร
- กำหนดสถานะผู้สมัครเป็น "รอตรวจสอบ"
- แสดงเฉพาะใบสมัครที่ส่งแล้วในรายการสำหรับเจ้าหน้าที่ตรวจสอบ

### Out of scope
- การตรวจสอบและอนุมัติใบสมัครโดยคณะกรรมการ
- การคัดเลือกผู้เข้าร่วมค่าย
- การจัดกลุ่มหรือฝ่ายงานของผู้เข้าร่วม
- การแก้ไขข้อมูลหลังส่งใบสมัคร
- การประกาศรายชื่อผู้ผ่านการคัดเลือก

## Constraints
- CON-ENR-01 แอปพลิเคชันรองรับค่ายเดียว โดย Backend ใช้ `CAMP_ID` จาก Environment Variable เพื่อระบุค่ายภายใน ต้องตรวจว่ามี record ค่ายดังกล่าวอยู่จริง ห้ามเลือกค่ายอื่นอัตโนมัติเมื่อไม่ได้กำหนดหรือไม่พบ record และต้องตรวจสถานะเปิดรับสมัครก่อนอนุญาตให้ส่งใบสมัคร
- CON-ENR-02 นักศึกษาต้องเข้าสู่ระบบก่อนดำเนินการสมัคร และเข้าถึงหรือแก้ไข Draft ได้เฉพาะของบัญชีตนเอง; การเรียก API จัดการ Draft โดยไม่มี Session ต้องถูกปฏิเสธด้วย HTTP 401 Unauthorized และ UI แจ้งให้เข้าสู่ระบบ
- CON-ENR-03 นักศึกษาต้องกรอกข้อมูลทุกฟิลด์ที่กำหนดให้ครบถ้วนก่อนยืนยันการส่งใบสมัคร แต่บันทึก Draft ที่ยังไม่ครบได้; ฟอร์มมีเฉพาะ `full_name`, `nickname`, `student_id`, `year_level`, `phone_number`, `contact_channel`, `food_allergy` และฟิลด์รายละเอียดแบบมีเงื่อนไข
- CON-ENR-04 `year_level` ต้องเป็น 1–6 หรือ `other` ที่มีรายละเอียด; `food_allergy` ต้องเป็น `no` หรือ `yes`; เมื่อเป็น `yes` ต้องมี `food_allergy_details`; เมื่อเป็น `no` ห้ามส่งรายละเอียดค้างอยู่; การสมัครไม่ต้องแนบเอกสาร
- IF-ENR-01 ระบบต้องตรวจสอบข้อมูลสมัครก่อนบันทึกเป็นใบสมัครที่ส่งแล้ว การบันทึก Draft ไม่ต้องผ่านการตรวจสอบความครบถ้วน
- IF-ENR-02 ระบบต้องตรวจสอบค่า `year_level` และเงื่อนไขข้อมูลการแพ้อาหารก่อนบันทึกเป็นใบสมัครที่ส่งแล้ว; ไม่รับหรือจัดเก็บเอกสารแนบใน flow สมัคร

## Requirements
- FR-ENR-01 ระบบต้องเปิดฟอร์มสมัครของค่ายเดียวที่ระบบกำหนดให้นักศึกษาโดยตรง โดยไม่ต้องเลือกค่าย   <- UC-11 main flow ขั้น 2
- FR-ENR-02 ระบบต้องให้นักศึกษากรอกเฉพาะชื่อ–นามสกุล (`full_name`), ชื่อเล่น (`nickname`), รหัสนักศึกษา (`student_id`), ชั้นปี (`year_level`), เบอร์โทรศัพท์ (`phone_number`), ช่องทางติดต่อ (`contact_channel`) และข้อมูลการแพ้อาหาร (`food_allergy`) พร้อมบันทึก/โหลด Draft ของตนเองหนึ่งรายการสำหรับค่ายนี้ได้   <- UC-11 main flow ขั้น 3
- FR-ENR-03 หากข้อมูลสมัครไม่ครบถ้วนเมื่อยืนยันการส่ง ระบบต้องแจ้งเตือนและระบุช่องข้อมูลที่ต้องแก้ไข โดยคงข้อมูลไว้เป็น Draft   <- UC-11 alternative flow 3a
- FR-ENR-04 ระบบต้องให้ผู้สมัครเลือกชั้นปี 1–6 หรือ “อื่นๆ (ระบุ)”; เมื่อเลือก “อื่นๆ (ระบุ)” ต้องกรอกรายละเอียด และระบบต้องปฏิเสธค่าชั้นปีที่ไม่อยู่ในรายการ
- FR-ENR-05 ระบบต้องให้ผู้สมัครเลือกข้อมูลการแพ้อาหาร “ไม่มี” หรือ “มี”; เมื่อเลือก “มี” ต้องกรอกรายละเอียดการแพ้อาหาร และเมื่อเลือก “ไม่มี” ต้องไม่ส่งรายละเอียดการแพ้อาหาร
- FR-ENR-06 เมื่อข้อมูลที่กำหนดครบและผ่าน validation ระบบต้องให้นักศึกษายืนยันการส่งข้อมูลสมัครโดยไม่ต้องแนบเอกสาร   <- UC-11 main flow ขั้น 5 (ปรับตาม CR)
- FR-ENR-07 เมื่อยืนยันการสมัครสำเร็จ ระบบต้องตรวจสอบและบันทึกข้อมูลเป็นใบสมัครสถานะ `submitted` ให้เจ้าหน้าที่เห็นในรายการตรวจสอบ และแสดงสถานะ "รอตรวจสอบ" แก่ผู้สมัคร   <- UC-11 main flow ขั้น 6

## Quality Requirements
- NFR-USE-01 นักศึกษาต้องสามารถกรอกข้อมูลและส่งใบสมัครได้โดยระบบแสดงข้อผิดพลาดใต้ช่องที่ไม่ผ่าน validation
- NFR-DATA-01 Draft และข้อมูลการสมัครที่ผ่านการตรวจสอบต้องถูกบันทึกอย่างถูกต้อง และเจ้าของต้องสามารถเรียกดูได้ภายหลัง
- NFR-SEC-01 ระบบต้องจำกัดการเข้าถึง Draft และข้อมูลการสมัครของนักศึกษาให้เฉพาะเจ้าของบัญชีหรือผู้ใช้งานที่มีสิทธิ์
- NFR-REL-01 ระบบต้องไม่บันทึกหรือแสดง Draft ที่ข้อมูลไม่ครบถ้วนหรือไม่ผ่าน conditional validation เป็นใบสมัครที่ส่งแล้ว

## Acceptance Criteria
- [ ] AC-ENR-01 (FR-ENR-01, FR-ENR-02)
        Given ระบบกำหนดค่ายเดียวและเปิดรับสมัคร และนักศึกษาล็อกอินเข้าสู่ระบบ
        When  นักศึกษาเข้าสู่ฟอร์มค่ายนั้นโดยตรง กรอกเฉพาะฟิลด์ที่กำหนด แล้วบันทึก Draft ก่อนออกจากระบบและกลับมาเข้าสู่ระบบด้วยบัญชีเดิม
        Then  ระบบต้องโหลดข้อมูล Draft สำหรับค่ายนั้นให้เจ้าของบัญชีเท่านั้น และแสดงข้อมูลไว้ก่อนยืนยันการส่ง; ฟอร์มต้องไม่มีช่องแนบเอกสาร และ Draft ยังไม่ถือเป็นใบสมัครที่ส่งแล้ว

- [ ] AC-ENR-02 (FR-ENR-03)
        Given นักศึกษาเข้าสู่ฟอร์มของค่ายเดียวโดยตรงและกรอกข้อมูลสมัครไม่ครบถ้วน
        When  นักศึกษากดยืนยันการสมัคร
        Then  Backend ต้องตอบ HTTP 422 พร้อมระบุ `field_name` ของทุกช่องที่ไม่ผ่าน; UI แสดงข้อผิดพลาดใต้ช่องนั้น; ระบบคงข้อมูลไว้เป็น Draft และไม่สร้างหรือแสดงใบสมัครที่ส่งแล้วในรายการตรวจสอบของเจ้าหน้าที่

- [ ] AC-ENR-03 (FR-ENR-04, FR-ENR-05)
        Given นักศึกษากรอกข้อมูลฟิลด์อื่นครบแล้ว
        When  นักศึกษาเลือกชั้นปี 1–6 หรือ “อื่นๆ (ระบุ)” และเลือก “ไม่มี” หรือ “มี” ในข้อมูลการแพ้อาหาร
        Then  ระบบต้องยอมรับชั้นปี 1–6; เมื่อเลือก “อื่นๆ (ระบุ)” ต้องแสดงช่องรายละเอียดและปฏิเสธหากว่าง; เมื่อเลือก “ไม่มี” ต้องซ่อน/ล้างรายละเอียดแพ้อาหาร; เมื่อเลือก “มี” ต้องแสดงรายละเอียดและปฏิเสธหากว่าง; ค่าชั้นปีที่ไม่ใช่ 1–6 หรือ `other` ต้องไม่ผ่าน; ไม่มีการตรวจหรือบังคับแนบเอกสาร


- [ ] AC-ENR-04 (FR-ENR-06, FR-ENR-07)
        Given นักศึกษากรอกข้อมูลครบถ้วนถูกต้องตาม CON-ENR-03 และ CON-ENR-04
        When  นักศึกษายืนยันการส่งข้อมูลสมัคร
        Then  ระบบต้องตรวจสอบและบันทึกข้อมูลโดยไม่ต้องแนบเอกสาร เป็นใบสมัครสถานะ `submitted` ในรายการตรวจสอบของเจ้าหน้าที่ และแสดงสถานะ "รอตรวจสอบ" แก่ผู้สมัคร

- [ ] AC-ENR-05 (NFR-DATA-01)
        Given นักศึกษาส่งข้อมูลสมัครครบถ้วนและระบบบันทึกสำเร็จ
        When  นักศึกษาตรวจสอบข้อมูลการสมัคร
        Then  ระบบต้องแสดงข้อมูลการสมัครที่บันทึกไว้และสถานะเป็น "รอตรวจสอบ"

## Assumptions & Open Questions

- ASM-01 นักศึกษามีบัญชีผู้ใช้งานและสามารถเข้าสู่ระบบได้ก่อนสมัคร
- ASM-02 ค่ายเดียวที่ Backend ระบุด้วย `CAMP_ID` ต้องอยู่ในสถานะ "เปิดรับสมัคร" ก่อนรับการส่งใบสมัคร
- ASM-03 รายการข้อมูลที่จำเป็นถูกกำหนดไว้ก่อนเปิดรับสมัคร
- ASM-04 เมื่อส่งใบสมัครและตรวจสอบข้อมูลสำเร็จ ระบบเก็บสถานะเป็น `submitted` และแสดงแก่ผู้สมัครว่า "รอตรวจสอบ"
- ASM-05 นักศึกษาสามารถสมัครเข้าร่วมค่ายได้เพียง 1 ครั้งต่อค่าย
- ASM-06 เมื่อใบสมัครถูกส่งแล้ว นักศึกษาจะไม่สามารถแก้ไขข้อมูลได้ด้วยตนเองจนกว่าจะมีการประกาศผู้เข้าร่วม และการแก้ไขข้อมูลภายหลังจะทำได้เฉพาะโดยคณะกรรมการ
- ASM-07 ตาม Change Request นี้ ฟอร์มใช้เฉพาะฟิลด์ที่ระบุใน FR-ENR-02 และไม่เพิ่มฟิลด์อื่นตามการตั้งค่าค่าย
- ASM-08 ตาม Change Request นี้ การสมัครไม่ใช้เอกสารแนบ; โครงสร้างตาราง/ข้อมูลเอกสารเดิมยังคงอยู่เพื่อรักษาข้อมูล legacy และไม่เป็นส่วนหนึ่งของ API, validation หรือ Mock API ปัจจุบัน; Demo Mode ใช้ Mock API ใน Development เท่านั้นและไม่ส่งคำขอไป Backend จริง
- ASM-09 Draft มีได้หนึ่งรายการต่อบัญชีผู้สมัครสำหรับค่ายเดียวที่ระบบกำหนด ผูกกับบัญชีเจ้าของเท่านั้น และเก็บข้อมูลฟอร์ม JSON ได้แม้ยังไม่ครบหรือยังไม่ผ่านการตรวจสอบ โดยไม่ต้องผ่าน Validation สำหรับการส่งใบสมัคร ผู้สมัครที่กลับมาเข้าสู่ระบบด้วยบัญชีเดิมต้องโหลดและแก้ไข Draft ของตนเองได้ Draft ไม่ถือเป็นใบสมัครที่ส่งแล้วและไม่ปรากฏในรายการตรวจสอบของเจ้าหน้าที่ เมื่อยืนยันการส่ง ระบบตรวจสอบข้อมูลตาม CON-ENR-03/04 หากไม่ครบให้แจ้งส่วนที่ต้องแก้ไขและคง Draft ไว้ หากผ่านให้สร้างใบสมัครสถานะ `submitted`
- ASM-10 ระบบจะแจ้งเตือนผู้สมัครเมื่อใบสมัครได้รับการอนุมัติ และผู้สมัครสามารถตรวจสอบสถานะใบสมัครได้จากระบบ
- Open Questions: ไม่มี

# Feature: แก้ไขข้อมูลผู้สมัคร (Edit Applicant Information)
Spec ID: SPEC-REG-002 | Source: UC-02 | Use case: UC-02
Owner: ทีมรับสมัคร/ค่าย | Status: Draft v2 | Updated: 2569-09-20

## Goal
คณะกรรมการสามารถค้นหาและแก้ไขข้อมูลรายละเอียดของผู้สมัคร/ผู้เข้าร่วมค่ายให้ถูกต้อง ครบถ้วน โดยระบบบันทึกประวัติการเปลี่ยนแปลงข้อมูล (Audit Trail) ทุกครั้ง เพื่อความโปร่งใสและตรวจสอบย้อนหลังได้

## Scope
### In scope
- ค้นหาและแสดงข้อมูลเดิมของผู้สมัครที่ต้องการแก้ไข
- ตรวจสอบความถูกต้องของข้อมูลใหม่ก่อนการบันทึก
- บันทึกการแก้ไขข้อมูลผู้สมัครลงฐานข้อมูล
- บันทึกประวัติการเปลี่ยนแปลง (Audit Log) ประกอบด้วย ผู้แก้ไข, วันเวลา, ข้อมูลเดิม และข้อมูลใหม่
### Out of scope
- การลงทะเบียน/กรอกใบสมัครใหม่ (UC-01)
- การคัดเลือกและประกาศผลผู้ผ่านการคัดเลือก (UC-05)
- การเข้าสู่ระบบและการจัดการสิทธิ์ของคณะกรรมการ (UC-00) - ถือว่ายืนยันตัวตนและมีสิทธิ์แล้ว (precondition)

## Constraints
- DOM-AUD-01 บันทึกประวัติการเปลี่ยนแปลง (Audit Log) ทุกครั้งที่มีการอัปเดตข้อมูลผู้สมัคร (ผู้แก้ไข, วันเวลา, ข้อมูลเดิม, ข้อมูลใหม่) และจัดเก็บไม่น้อยกว่าระยะเวลาที่โครงการกำหนด
- DOM-TXN-01 การอัปเดตข้อมูลผู้สมัครและการสร้าง Audit Log ต้องทำงานภายใต้ Transaction เดียวกัน (Atomicity)
- SEC-RBAC-01 ผู้ใช้งานต้องมีบทบาท (Role) เป็น "คณะกรรมการ" หรือ "ผู้ดูแลระบบ" จึงจะมีสิทธิ์เข้าถึงและแก้ไขข้อมูล

## Requirements
- FR-REG-01 ระบบต้องรองรับการค้นหาและแสดงรายละเอียดข้อมูลเดิมของผู้สมัครตามที่คณะกรรมการระบุ เพื่อให้สามารถตรวจสอบและแก้ไขข้อมูลทุกฟิลด์ที่อนุญาตบนแพลตฟอร์มได้  <- UC-02 main flow ขั้น 1-2
- FR-REG-02 ระบบต้องตรวจสอบความถูกต้องของข้อมูลใหม่ (Data Validation) ก่อนดำเนินการบันทึก โดยยึดรูปแบบทั่วไป เช่น ชื่อต้องไม่มีตัวเลข และเบอร์โทรศัพท์ต้องไม่มีตัวอักษร  <- UC-02 main flow ขั้น 4
- FR-REG-03 เมื่อพบข้อมูลไม่ถูกต้อง ระบบต้องปฏิเสธการบันทึก แสดงข้อความแจ้งเตือน และคงค่าที่กรอกไว้ให้แก้ไข  <- UC-02 alternative 3a
- FR-REG-04 เมื่อคณะกรรมการกดยืนยันและข้อมูลถูกต้อง ระบบต้องบันทึกข้อมูลใหม่ลงฐานข้อมูล และอนุญาตให้แก้ไขทุกฟิลด์บนแพลตฟอร์มที่เปิดให้ใช้งาน  <- UC-02 main flow ขั้น 6
- FR-REG-05 ระบบต้องบันทึกประวัติการเปลี่ยนแปลงข้อมูล (Audit Log) ต่อการกดยืนยันครั้งเดียว โดยระบุผู้แก้ไข วันเวลา ฟิลด์ที่แก้ไข ค่าเดิม และค่าใหม่ สำหรับทุกฟิลด์ที่เปลี่ยนแปลง  <- UC-02 main flow ขั้น 6
- FR-REG-06 เมื่อคณะกรรมการกดยกเลิก ระบบต้องยกเลิกการแก้ไข คืนค่าสถานะเดิมให้ฟอร์ม และปิดฟอร์มโดยไม่บันทึกประวัติใดๆ  <- UC-02 alternative 5a

## Quality Requirements
- NFR-PERF-01 เวลาตอบสนองในการบันทึกข้อมูลพร้อมสร้าง Audit Log ต้องมีค่าเฉลี่ย <= 1.5 วินาที
- NFR-SEC-01 ป้องกันการแก้ไขข้อมูลจากผู้ใช้ที่ไม่มีสิทธิ์ตามหลัก Least Privilege
- NFR-USE-01 ระบบต้องเน้นช่องข้อมูลที่มีข้อผิดพลาด (Highlight error fields) พร้อมข้อความแนะนำที่ชัดเจน

Acceptance Criteria
- [ ] AC-REG-01 (FR-REG-04, FR-REG-05)
        Given คณะกรรมการเปิดหน้าข้อมูลผู้สมัคร
        When  แก้ไขเบอร์โทรศัพท์ติดต่อและกด "ยืนยัน"
        Then  ระบบบันทึกข้อมูลใหม่ และสร้างประวัติการเปลี่ยนแปลงระบุผู้แก้ไข วันเวลา ฟิลด์ เบอร์เดิม และเบอร์ใหม่
- [ ] AC-REG-02 (FR-REG-02, FR-REG-03)
        Given คณะกรรมการอยู่ในหน้าแก้ไขข้อมูล
        When  กรอกข้อมูลในรูปแบบที่ไม่ถูกต้อง (เช่น เบอร์โทรศัพท์ไม่ครบ 10 หลัก) แล้วกดยืนยัน
        Then  ระบบแจ้งเตือนให้แก้ไข ไม่บันทึกข้อมูลลงฐานข้อมูล และไม่มีการสร้างประวัติการแก้ไข
- [ ] AC-REG-03 (FR-REG-06)
        Given คณะกรรมการเปลี่ยนข้อมูลในฟอร์มแก้ไข
        When  กดปุ่ม "ยกเลิก"
        Then  ระบบยกเลิกการเปลี่ยนแปลง แสดงข้อมูลเดิม และไม่มีการสร้างประวัติการแก้ไข

## Assumptions & Open Questions
- ASM-01 ผู้สมัครมีข้อมูลอยู่ในระบบแล้ว (Precondition)
- ASM-02 การนับวันเวลาในการบันทึก Audit Log อ้างอิง Timezone Asia/Bangkok
- ASM-03 การแก้ไขข้อมูลผู้สมัครอนุญาตให้แก้ไขได้ทุกฟิลด์บนแพลตฟอร์มที่แสดงอยู่ และต้องมีการบันทึก Audit Log ทุกครั้งที่กดยืนยัน
- ASM-04 การแก้ไขข้อมูลจะปิดการใช้งานทันทีเมื่อกระบวนการลงทะเบียนเสร็จสิ้นแล้ว
- ASM-05 การตรวจสอบความถูกต้องใช้กฎรูปแบบทั่วไป เช่น ชื่อต้องไม่มีตัวเลข และเบอร์โทรศัพท์ต้องไม่มีตัวอักษร
- ASM-06 Audit Log จะบันทึกต่อการกดยืนยันครั้งเดียว และเก็บค่าเดิมและค่าใหม่ของฟิลด์ที่เปลี่ยนแปลงเท่านั้น
- ASM-07 เมื่อกดยกเลิก ระบบจะคืนค่าเป็นข้อมูลเดิมและปิดฟอร์ม โดยไม่คงการแก้ไขหลังจากยกเลิก
